## 2. 一处判断修正：瓶颈不在写入

审计稿的 §0 把 O(T²) 归因于"写入是 O(n)"，据此把倒排索引排在第一位。方向对，但**归因不完整**：

```
一次 ingest 的真实成本（v0.5.1，822 cell）
  去重      全表 Jaccard 扫描       ← 审计稿指出的那一段
  冲突检测  全表扫描                ← 同上
  ────────────────────────────────
  Q1 语义路 forEachCell + cosine    ← 审计稿没算这一段
  面板 stats/doctor 各一次全表解码  ← 审计稿没算这一段
```

实测把三段分开测之后，**写入只占一小半**：真正吃时间的是"为了算 128 次乘加，把每条 cell 的  
MC03 blob 解一遍"。所以本版的顺序是：

1. **先削掉"为了一个小数字解码全库"**（Q1 向量矩阵、`stats` 改聚合、`doctor` 合并单趟）；
2. **再削掉"为了找一个近似项全表比一遍"**（SDR 倒排、冲突索引、时间索引）。

两项都做完，822 cell 的每轮耗时从 25.4 ms 掉到 3.1 ms，且**趋势变平**——  
这比"把某一段加速 10 倍"更重要：趋势平坦才叫"站得住"。

## 3. 修复方案（按落地顺序）

### 3.1 向量矩阵（`core/src/emb.ts`）—— 收益最大的一项

`emb` 只存在 blob 里，没有列。给它加一列要多 128 B/cell，而整条 cell 才 342 B——  
存储比会从 0.839 涨到 1.1 以上，等于用一个**被验收过的指标**换一个没被验收的。

所以做成内存矩阵：`Int8Array` 连续缓冲 + 稠密下标 + 预计算范数。  
冷层 32 维 PQ 向量在**写入索引时**用与 `cosine()` 完全相同的 `expandEmb` 展开到统一维度，  
所以索引给出的分数与逐条 `cosine()` **逐位相同**，不是近似索引。

收益：Q1 从"解 N 个 blob"变成"扫 12.8 MB 连续内存"，10 万 cell 约 1 ms。

### 3.2 SDR 倒排（`core/src/inverted.ts`）

`Map<bit, denseId[]>`，懒构建、增量维护、超预算停用并**上报** `RuntimeStatus`。

**阈值不是拍的，是由判定门限反推的必要条件**：

```
Jaccard  J = o/(|a|+|b|−o)  ⟹  o = J(|a|+|b|)/(1+J) ≥ J·|a|/(1+J)
containment C = o/|a|       ⟹  o = C·|a|
```

于是候选集是真实候选的**超集**，不漏召回——这一点和 ANN 有本质区别，  
也是它敢接进写路径（去重，写错会丢数据）的理由。

`candidatesByOverlap` 返回 `{id, overlap, size, kind}`，让去重可以**完全不回表**算精确 Jaccard

|        |   |   |   |                                       |
| ------ | - | - | - | ------------------------------------- |
| （\`o/( | a | + | b | −o)`三个量索引都有），只有"真要合并"时才`getCell\` 一次。 |

|   |   |   |   |   |   |
| - | - | - | - | - | - |

### 3.3 冲突索引：从 `agent|pred` 到 `agent|pred|manner|patient|polarity`

|                                                         |                                         |
| ------------------------------------------------------- | --------------------------------------- |
| 第一版按 \`agent                                            | 谓词家族\` 分桶——而用户的 agent 永远是"用户"、谓词只有六个家族， |
| 桶里躺着全库 1/6 的 cell。实测 400 条时桶大小就是 400，`findConflict` 退化成 |                                         |
| "每次 ingest 解 400 个 blob"（profile 里 `getCell` 占 65%）。    |                                         |

真正决定"这两条会不会矛盾"的是**同客体或同方式**，且同客体时还需要**极性相反**。  
键里带上这些之后，400 cell 下每次 ingest 的 `getCell` 从 **2026 次/5 轮降到 16 次/5 轮**（127×）。

### 3.4 时间路走现有索引（成本最低的一项）

`idx_time(t_from, t_to)` 从 v0.2 就建着，Q4 却一直 `forEachCell`。  
改成 SQL 区间查询即可。口径保持与原来**逐条一致**（只比 `tFrom`，不看 `tTo`），  
并由 `test/v052-index` 的"索引结果 == 全扫结果"对拍。

### 3.5 保留度落盘 + 单调性剪枝（D24）

新增 `retention(cell_id, score, band, at)` 表（**不改 cells 表**，旧库无需 rebuild）。  
只存 score/band/at：七因子分解是面板逐条展示的内容，缓存成 JSON 会让存储涨约 20%，  
而面板只算最近 120 条（实测 2 ms），不值得。

**失效传播统一收口到三处**：召回命中（`tAccess`/`stability` 变）、`coactivate` 加边、  
`upsertMeta` 写元数据。降档本身**不作废**缓存——因为 `tier` 不是七因子的输入，  
所以"降了一级之后该不该继续降"的结论仍然有效，逐级下降因此走快路径。

> 第一版在降完就 `invalidateRetention`，结果 `demotableByCache` **永远返回空**：  
> 缓存只可能存在于"评估过但没降"的条目上，而那些本来就不该降——剪枝成了死代码。  
> 这个问题是被 `test/v052-retention-cache` 的第一条用例抓住的。

**增量扫描**：一次 pass 只评估 `demoteBatch`（默认 2000）条**最久未被评估**的 cell，  
于是单次 tick 的成本与库规模无关，全库扫描由多个 tick 分摊。

**整段包一个事务**：`setRetention` 是 `INSERT ... ON CONFLICT`，不包事务时每条语句一次  
WAL 提交。实测 1 万 cell 的一次 pass 从 **2066 ms 降到 658 ms**——97% 的时间原本花在 fsync 上。

### 3.6 面板热路径（审计稿没提，但同样是规模问题）

`panelSnapshot()` 每 3 秒被调一次，而它原来要：  
`stats()`（全表解码）+ `allEdges()`（整张边表）+ `doctor()`（三次全表解码）+ `retentionView()`（`allEdges` 又一次）。

四处一起改：

| 位置                | 原来                 | 现在                                      |
| :---------------- | :----------------- | :-------------------------------------- |
| `stats()`         | `forEachCell` 数几个数 | SQL `GROUP BY`（10k cell：20 ms → 0.8 ms） |
| `allEdges()`      | 全表再切片              | 加 `limit` 参数，SQL `LIMIT`                |
| `doctor()`        | 三次 `forEachCell`   | 合并单趟 + 面板侧 30 秒缓存                       |
| `retentionView()` | `allEdges` 算度数     | 只对要展示的 120 条查两次索引                       |

### 3.7 确定性小修（D20–D23、D27）

见 §1.2 表格。每条各带一条回归测试。

### 3.8 文档口径闭环（D28）

`check-readme.mjs` 增加三项：

- **命令数**：从 `commands.ts` 的 `case '<verb>'` 实测，与英/中两份 README 比对；
- **命令存在性**：文档里出现的 `/mnemo <verb>` 必须在 `commands.ts` 里有实现  
  （这条挡的是"文档有、代码无"）；
- 测试数在 `lib/` 缺席时退回**静态计数**并标明口径。

`/mnemo trace` 补上实现（`why` 回答单条，`trace` 回答整次检索走了哪几条路）。

## 5. 兼容性、风险与口径

- **存储布局**：MC03 不变。`retention` 是新表，不碰 `cells`，**旧库不需要 rebuild**。
- **内存**：10 万 cell 时倒排 ≈ 16 MB、向量矩阵 ≈ 12.8 MB，合计约 29 MB；  
  超 `sdrMaxCells`（默认 20 万）整体停用并退回全扫，`RuntimeStatus.sdrIndex` 如实上报。
- **倒排的最大风险是漏召回**。这里的防线是"由门限反推必要条件"（§3.2），  
  候选集是超集而不是近似；再加 `Recall@8 0.941 不退化` 兜底。
- **剪枝的正确性依赖 v0.5.1 的单调性**。它错的时候很安静（只影响"哪些被降"），  
  所以验收是扫描式的：`test/v052-retention-cache` 用"小批量 vs 大批量跑到收敛后比对"。
- **合成语料不是真实库**。它用批量 `putCell` + 合成边造出来，没有残差、访问历史均匀，  
  所以**只回答"多快"，不回答"准不准"**。这个口径写进了 `bench-scale.json` 的 `caveat` 字段、  
  控制台输出与 README——否则后代会拿它当真实数据引用，那正是 D13 走过的老路。

## 6. 暂时不做

| 不做                             | 理由                                                                                     |
| :----------------------------- | :------------------------------------------------------------------------------------- |
| **真 embedding（P0-1）**          | 它在全扫框架下只会更贵。要先有"O(候选)"的检索结构，质量收益才兑现——本版做的正是那个结构，但换 embedding 会引入 ONNX 依赖，是 v0.6 的产品级议题 |
| **读侧 τ ≥ 4**                   | 剪枝比很诱人（130×），但候选占比 0.77% 会漏真阳性。先落"由门限反推"的精确版                                           |
| **D26 两驱动残余引用语义统一**            | 影响面小（MemoryStore 只用于测试与 bench），但改动涉及 `residualRefs` 的语义定义                              |
| **D19 联想抑制**                   | 会改 ASSOC 边权语义，与倒排同版做会互相干扰验证                                                            |
| **倒排落表**                       | 10 万 cell × 40 bit = 400 万行；重启时读回 400 万行比"一次全扫解码 10 万条 blob"更慢。内存 + 懒构建是实测后的选择，不是偷懒    |
| **P0-2 L1 走真模型 / P0-5 情绪识别升级** | 依赖宿主接缝与标注集，与规模化正交                                                                      |

## 附：本次审计与验证的方法

结论全部来自可复现的操作：

```bash
npm ci && npm run build && npm test        # 176 pass
npm run typecheck && npm run check         # 13 项 SDR 性质
npm run check:readme                       # 规模/测试/缺点/命令数

npm run bench:corpus                       # 1 万 cell 合成语料
node scripts/bench-scale.mjs --corpus 10000 --ab   # 索引开关对照（11× / 21×）
npm run ci:assert-scale                    # 规模门槛
```

`--cpu-prof` 的两轮归因（改动前后）是 §2 与 §3.3 结论的来源：  
改动前 `getCell` 占 33%、其中 65% 来自 `findConflict`；改动后同一路径降到 3.5%。

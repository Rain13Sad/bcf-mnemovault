# v0.5.2 — 让它在真实规模上站得住

> 发布日期：2026-10-31 · 基线 DSH `0.2.1-rc.3` · 存储布局 MC03（**旧库不需要 rebuild**）

0.5.0 让决策链会算，0.5.1 让它算对。0.5.2 让它**在真实规模上仍然成立**。

这一版最有价值的部分不是"快了多少"，而是**把审计稿的归因纠正了**：
瓶颈不是"写入 O(n)"，而是"为了算 128 次乘加，每次召回都把全库的 MC03 blob 解一遍"。
修完之后，每轮耗时**不再随规模增长**——这比任何单点数字都重要。

## 二、做了什么

### 1. 向量矩阵：不再为 128 次乘加解码全库

`emb` 只存在 blob 里，没有列。给它加一列要多 128 B/cell，而整条 cell 才 342 B——
存储比会从 0.839 涨到 1.1 以上。所以做成**内存矩阵**：连续 `Int8Array` + 稠密下标 + 预计算范数。

关键在一致性：冷层 32 维 PQ 向量在**写入索引时**用与 `cosine()` **同一个** `expandEmb` 展开，
所以矩阵给出的分数与逐条 `cosine()` 逐位相同。这不是近似索引。

### 2. SDR 倒排：阈值由门限反推，不是拍的

```
Jaccard  J = o/(|a|+|b|−o)  ⟹  o = J(|a|+|b|)/(1+J) ≥ J·|a|/(1+J)
```

于是候选集是真实候选的**超集**——不漏召回。这是它敢接进写路径（去重）的理由，
也是它和 ANN 的本质区别。更进一步：`candidatesByOverlap` 返回 `{id, overlap, size, kind}`，
于是 Jaccard 可以**完全不回表**算出来，只有"真要合并"时才 `getCell` 一次。

### 3. 冲突索引：桶里不该躺着全库的 1/6

原来按 `agent|pred` 分桶，而用户的 agent 永远是"用户"、谓词只有六个家族——
400 条时桶大小就是 400，`getCell` 占 profile 的 65%。
真正决定"会不会矛盾"的是**同客体或同方式**，且同客体时还需要**极性相反**。
键带上这些之后，每 5 轮的 `getCell` 从 **2026 次降到 16 次**。

### 4. 保留度落盘 + 单调性剪枝

新增 `retention(cell_id, score, band, at)` 表（**不改 `cells`**，旧库无需 rebuild）。
一次 pass 只评估 `demoteBatch` 条最久未评估的 cell，整段一个事务。

两个实现细节值得单独说，因为它们都是"写完才发现不成立"的：

- **降档不能作废缓存**。第一版在降完就删缓存，结果 `demotableByCache` 永远返回空——
  缓存只可能存在于"评估过但没降"的条目上，而那些本来就不该降，剪枝成了死代码。
  `tier` 不是七因子的输入，所以降了一级之后"该不该继续降"的结论仍然有效。
- **整段要包一个事务**。`setRetention` 是 `INSERT ... ON CONFLICT`，不包事务时每条语句
  一次 WAL 提交：10k 的一次 pass 2066 ms，其中 **97% 花在 fsync 上**。

### 5. 面板热路径

面板每 3 秒刷新一次，而它原来要：`stats()`（全表解码）+ `allEdges()`（整张边表）+
`doctor()`（三次全表解码）+ `retentionView()`（又一次 `allEdges`）。四处一起改：
SQL `GROUP BY`、`allEdges(limit)`、doctor 合并单趟 + 30 秒缓存、保留度只对 120 条查索引。

### 6. 九个确定性缺陷（D20–D28）

| # | 缺陷 | 修法 |
| :--- | :--- | :--- |
| D20 | `explain()` 非只读召回 | `readOnly: true` |
| D21 | schema 的 `FLAG.noDecay & 0` 恒为 0 | `FLAG.noDecay` |
| D22 | `maxResidualBytes` 按 UTF-16 码元截断 | 按 UTF-8 字节、切在码点边界 |
| D23 | 短 id 两份实现、碰撞静默取第一个 | 合并 + `AmbiguousCellIdError` |
| D24 | 保留度不落盘 | 见上 |
| D25 | 基准不测真实路径 | 规模门槛进 CI |
| D26 | 两驱动残余引用语义不等价 | **未修**（已记录，影响面小） |
| D27 | 写路径不走语句缓存 | 全部 `prep()` |
| D28 | 文档口径漂移 | `check-readme` 校验命令数与命令存在性 |

## 三、测试

- **160 → 176**，全绿；`npm test` 耗时从 300 s+（超时）降到 **5 s**（解码不再吃满 CPU）。
- 新增 16 条，其中 6 条是"扫描式"而不是单点采样：
  - 倒排阈值是**必要条件**（随机 200 对 SDR 验证）、候选是**超集**（与全扫对拍）；
  - 时间路索引结果与全扫**逐条一致**；
  - 剪枝只"提前降"不"提前不降"；增量与全量**收敛到同一结果**；
  - 索引在外部写入后**自愈**（这条抓出了一个真 bug：重建时漏带 `kind`）。

另有一条也是被测试抓出来的：倒排一开始返回的 `overlap` 是门限值而不是真实位数，
于是 Jaccard 被算小、**去重静默失效**（"同一句说两次"产生了两个 cell）。

## 四、CI

修掉一处红灯：`npm-latest` job 没有 `build`，而 `check:readme` 会跑测试拿真实条数，
`lib/` 不在 → 测试全失败 → 报"拿不到 # tests N"。两处一起修（job 补 build；
脚本在 `lib/` 缺席时退回静态计数并标明口径）。

新增：`verify` job 跑 `ci:assert-scale`（1 万 cell，`recall p95 ≤ 40 ms`）。
README 里那个数字从 v0.3 就写着，CI 里**从来没有断言过**。

## 五、升级

```bash
npm i @rain13sad/dsh-mnemo-core@0.5.2
```

- **不需要 rebuild**：MC03 不变，`retention` 是新表。
- 首次 `open()` 后索引懒构建（1 万 cell 约 300 ms），期间照常工作，只是退回全扫。
- 超过 `index.sdrMaxCells`（默认 20 万）时索引整体停用并**如实上报**到 `RuntimeStatus.sdrIndex`，
  面板能看到"退回全扫"，不会静默降级。
- 新增配置（都有默认值）：`index.sdrEnabled` / `index.sdrMaxCells` / `index.demoteBatch` /
  `index.retentionTtlMs`。

## 六、已知取舍

- **合成语料不是真实库**（见 §1 的口径说明）。
- **倒排是内存态**，重启后第一次用到时重建。落表要 400 万行（10 万 cell），
  读回比重扫一遍更慢——这是实测后的选择，写在设计文档 §6。
- **D26 未修**：两驱动的残余引用语义仍需一次明确的语义决定。
- **剪枝依赖 v0.5.1 的单调性**。它错的时候很安静（只影响"哪些被降"），
  所以验收是扫描式的，不是单点采样。

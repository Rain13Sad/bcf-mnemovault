# v0.5.3 桌面版安装缺陷与修复

> 现场：DSH Desktop `0.2.1-rc.3`（Electron，内置 pnpm `11.28.5`）· profile `~/.dsh/profiles/desktop`
> 时间：2026-10-31 夜 · 操作人：维护者本机 · 结果：**装上了，但文档给的那条命令装不上**

这份文档不是发布说明，是**现场报告 + 修复单**。它记录的是"把 0.5.3 真的装进桌面版"这

（D2 / D3 / D4）。它们的共同点是：**没有任何测试在跑真实的安装器**。
（D8 是 11-01 卸载时补记的，同一个根：安装器这条路径没人测。）

## 二、缺陷清单

### D1 · P1 · 代码 · 首次安装后 7 层起不来

**症状**（原文）：

```
dsh: warning: 7 entries did not activate
mnemo-core (@rain13sad/dsh-mnemo-core): Error: unable to open database file
    at SqliteStore.open (.../dsh-mnemo-core/lib/store.js:505:20)
mnemo-encoder (@rain13sad/dsh-mnemo-encoder): pending (waiting for service: memory)
mnemo-recall … pending    mnemo-tools … pending    mnemo-consolidator … pending
mnemo-settings … pending  mnemo-proactive … pending
```

**根因**：`SqliteStore.open()` 直接 `new DatabaseSync(path)`，**从不创建父目录**。
默认库路径是 `~/.dsh/mnemo/vault.db`，而 `~/.dsh/mnemo` 在任何全新机器上都不存在。
`node:sqlite` 对不存在的目录只抛一句 `unable to open database file`。

**为什么难查**：症状离原因很远。真正失败的只有 1 层，但另外 6 层因为
`inject: ['memory']` 全部停在 pending——用户看到的是"面板在、但一条记忆都没有"，
而面板此时连降级提示都给不出（快照从来没被写出来）。

**修复**（`packages/core/src/store.ts`）：

```diff
+import { mkdirSync } from 'node:fs'
+import { dirname } from 'node:path'

 export class SqliteStore implements Store {
   open(): void {
     if (this.db) return
+    // 父目录归插件管：宿主不会替我们建 ~/.dsh/mnemo。
+    // 少了这一行，全新机器上 core 必然激活失败，而症状会甩给下游 6 层。
+    if (this.path !== ':memory:' && !this.path.startsWith('file::memory:')) {
+      mkdirSync(dirname(this.path), { recursive: true })
+    }
     const mod = builtin<…>('node:sqlite')
     const db = new mod.DatabaseSync(this.path)
```

**验收**：删掉 `~/.dsh/mnemo`，重启，`vault.db` 自动出现且启动输出**没有** `did not activate`。

### D2 · P1 · 文档/流程 · README 的主安装命令今天装不上

**症状**：照 README 的九包一行命令装，pnpm 装的是 **`0.5.0`**：

```
+ @rain13sad/dsh-mnemo-core 0.5.0
dsh: installation rejected: Cannot validate installed package @rain13sad/dsh-mnemo-core:
  YAMLException: cannot resolve a node with !<tag:yaml.org,2002:js> explicit tag (6:22)
dsh: restored package.json, pnpm-lock.yaml, and node_modules.
```

**根因**：pnpm 11 的 **`minimumReleaseAge`** 年龄门槛。它会把"太新"的版本从解析结果里剔掉。
实测行为与 **24 小时** 一致：安装发生在 `0.5.3` 发布后 56 分钟、`0.5.2` 发布后 19.6 小时，
两者都不可见，于是落到 28 小时前的 `0.5.0`。
而 0.5.0 恰好是**带 `!!js` 的那一版**——安装期校验必然拒绝。

这不是 0.5.3 引入的问题，但 0.5.3 的发布方式（连续两天发三版）正好把它踩实了：
**用户照文档装，永远拿到一个坏版本，而且错误信息指向 YAML 而不是"你的版本太旧"。**

**修复**（文档，五份 README + `docs/PROJECT-GUIDE.md`）：主命令改为**钉版本**。

```bash
dsh plugin --profile desktop add \
  @rain13sad/dsh-mnemo-core@0.5.3 @rain13sad/dsh-mnemo-affect@0.5.3 \
  @rain13sad/dsh-mnemo-encoder@0.5.3 @rain13sad/dsh-mnemo-recall@0.5.3 \
  @rain13sad/dsh-mnemo-consolidator@0.5.3 @rain13sad/dsh-mnemo-proactive@0.5.3 \
  @rain13sad/dsh-mnemo-tools@0.5.3 @rain13sad/dsh-mnemo-settings@0.5.3 \
  @rain13sad/dsh-mnemo-ui@0.5.3
```

需要"永远装最新"时，显式关掉年龄门槛（已验证可用）：

```bash
dsh plugin --profile desktop add <包名...> --config.minimumReleaseAge=0
```

**验收**：在一个空的临时 profile 里跑上面两条，`dsh plugin list` 都应是 `0.5.3`。

### D3 · P1 · 文档 · 桌面版的 profile 必须由应用先初始化

**症状**：

```
dsh: Error: Open DeepSeek Harness Desktop once to initialize its profile,
     then fully quit it before running dsh plugin --profile desktop.
```

**根因**：桌面 profile 的 `package.json` 由 Electron 主进程在 `applyRelease()` 里写
（`DesktopProjectManager.createPluginProfile` → `initProfile`）。CLI 侧只做
`existsSync(join(profileDir,'package.json'))` 这一个判断——文件不在就直接拒绝。

本机的情况是：`cordis.patch.yml` 和 `pnpm-workspace.yaml` 都在（10-21 建的），
`package.json` 却没有。也就是说**这个 profile 曾经初始化过一半**，而 CLI 对"半个 profile"
没有任何自愈能力，也不会告诉你怎么补。

**修复**（文档）：桌面版安装写成三步，且把"为什么"写进去：

1. 打开一次 DeepSeek Harness Desktop（生成 `~/.dsh/profiles/desktop/package.json`）；
2. **完全退出**（托盘也要退，profile 有独占锁）；
3. 再跑 `dsh plugin --profile desktop add …`，或直接在设置 → 插件里装。

顺带记一条排障口令：`ls ~/.dsh/profiles/desktop/package.json`。没有这个文件，后面所有
CLI 命令都会用 D3 那句话拒绝你。

### D4 · P2 · 文档 · README 的验证命令在桌面版上不成立

README 让你这样确认"某一层真的挂上了"：

```bash
dsh --profile <名字> --dump-config | grep mnemo
```

桌面版直接拒绝：

```
error: profile "desktop" is managed exclusively by the Electron application
```

**根因**：`--dump-config` 走的是"启动 profile"的路径，桌面 profile 在 `parseDshArgs` 里
对非 `plugin` 子命令一律拒绝（只有 `dsh plugin` 带 `manageDesktopProfile: true` 放行）。

**修复**（文档）：桌面版改用**能跑的那条**——

```bash
dsh plugin --profile desktop list --depth 0    # 看依赖
```

要看组合树，得把依赖复制到一个非桌面 profile（本次用的就是这个办法）：

```bash
mkdir -p ~/.dsh/profiles/mnemo-check
cp ~/.dsh/profiles/desktop/{package.json,pnpm-workspace.yaml} ~/.dsh/profiles/mnemo-check/
# 把 package.json 的 name 改掉，然后：
dsh plugin --profile mnemo-check install
dsh --profile mnemo-check --dump-config | grep -A2 mnemo
```

（本次验证结果：`mnemo-affect / -consolidator / -core / -encoder / -proactive / -recall /
-settings / -tools / -ui` 九行齐全，`mnemo-core` 的 config 里**没有** `dbPath`——
符合 0.5.3 的设计：路径在 `apply()` 里解析。）

### D5 · P2 · 代码 · `embStoreDim` 有两个默认值，而它参与布局键

**症状**（用 README 里那段 `new MemoryService` 打开宿主建的库）：

```
[mnemo] 布局不匹配：库为 2048:8:64:3，配置为 2048:8:128:3。
```

**根因**：同一个字段有两张默认值表。

| 来源 | `embStoreDim` | 谁在用 |
| :--- | :--- | :--- |
| zod schema `Config`（`index.ts:35`） | **64** | 宿主：Loader 用 schema 默认值补全 patch |
| `defaultConfig()`（`index.ts:107`） | **128** | README 片段、devkit、测试、bench |

后果是分裂的：

- 真实安装出来的库是 **64 维**（每条 cell 的向量 64 B）；
- 文档（五语 README + PROJECT-GUIDE）写的是 **341 B/条、折叠到 128 维**——按 64 维算应是约 **277 B**；
- 任何照着 README 写 `defaultConfig({ dbPath })` 的人，打开自己的库会**被布局键挡住**，
  而错误信息让他去 `/mnemo rebuild --from-log`——一个本来不该发生的数据迁移。

**修复方向（重要，别选错）**：**把 `defaultConfig()` 改成 64，而不是把 schema 改成 128。**
因为 0.5.3 已经发出去、已经有人装了，他们盘上的库就是 `…:64:3`；改 schema 等于让所有
存量库在升级后拒绝启动。64 是既成事实，也是错误文案里写的那个数。

```diff
 export function defaultConfig(overrides: Partial<MnemoConfig> = {}): MnemoConfig {
   return applyPreset({
     …
-    embStoreDim: 128,
+    embStoreDim: 64,
```

配套三件事，缺一件都不算修完：

1. **加一条守卫测试**（`test/config-defaults.test.mjs`）：对**参与布局键**的四个字段
   （`sdrDim` / `sdrK` / `embDim` / `embStoreDim`）断言
   `defaultConfig()[k] === Config.parse({})[k]`。这条测试的存在，比修好这次更重要。
2. **重跑 bench** 并同步 `artifacts/bench.json`（存储比会变好，门槛不会被打破）。
3. **改文档数字**：五份 README + `docs/PROJECT-GUIDE.md` 里的 `341 B` → `277 B`
   （`n × 341` 的公式同步改），改完跑 `npm run check:readme`。

长期解（0.5.5）：`defaultConfig()` 直接以 `Config.parse({})` 为底，只覆盖 `dbPath: ':memory:'`
这类"测试专用"差异——**一个字段只能有一张默认值表**。

### D6 · P2 · 代码 · `ui` 声明了一个不存在的 client 依赖

`packages/ui/package.json` 的 `dsh.client.inject` 里有：

```json
"@deepseek-ai/dsh-client-ui-slots"
```

而 `0.2.1-rc.3` 的运行时里**没有这个包**（既不是 `dsh/package.json` 的依赖，asar 里也没有文件）。
实测宿主照样把我们的 `client.js` 排进了模块图，`client-modules` 的 `arriveGraphRow` 对
解析不到的 inject 项是**静默跳过**的：

```js
for (const packageName of row.inject) {
  const dependency = this.graphRows.get(packageName)
  if (dependency !== void 0) await this.arriveDependency(…)
}
```

所以这一条**今天不会白屏**，但它是一颗哑弹：一旦宿主的加载器改成"缺依赖即失败"，
面板会整块消失，而错误会指向 `dsh-client-ui-slots`——一个我们根本不需要的包。

**修复**：删掉该行；`check:manifests` 加一条规则——`dsh.client.inject` 里每一项都必须是
**本包 dependencies 或宿主运行时依赖**之一（离线可校验的那部分先卡住，运行时那部分留给 D1 类 smoke）。

### D7 · P3 · 体验 · 面板的"跳过原因"每分钟刷一条同样的记录

快照里 `proactive.skipped` 四条记录的时间戳间隔正好 60 秒，原因全是
`静默时段 23:00–8:00`。列表上限 20（`proactive/src/index.ts:205`），也就是面板上永远显示
"最近 20 分钟都在静默"——这条信息在第一次之后就没有增量价值，却把真正的原因
（比如"没有值得提的由头"）挤出了窗口。

**修复**：同一 `reason` 连续出现时只更新时间戳、不新增记录（去重窗口 10 分钟），
列表上限降到 8。

### D8 · P2 · 契约 · 卸载命令自相矛盾（2026-11-01 补记）

**症状**：`dsh plugin --profile desktop remove <九个包>` 直接失败：

```
[ERR_PNPM_CANNOT_REMOVE_MISSING_DEPS] Cannot remove '@rain13sad/dsh-mnemo-core', …
  : project has no dependencies of any kind
```

**但**：命令返回时 `package.json` 的 `dependencies` 与 `dsh.profile.bundles` **已经被清空了**。

**根因**：`dsh plugin` 先把这些包从 profile 清单里摘掉（reconcile），再把原始参数交给
`pnpm remove`。pnpm 读到的清单里已经没有这些依赖，于是拒绝——**remove 要求"清单里还有它"，
而 dsh 自己先把前提删了**。

**后果是"半完成"而不是"没做"**：清单干净、`pnpm-lock.yaml` 干净，但 `node_modules` 里还剩
5 个包（另外 4 个已被 pnpm 删掉）。用户看到非零退出码会以为没卸干净，重跑一次得到同样的错。

**绕过**（本次用的，已验证）：

```bash
dsh plugin --profile desktop install     # pnpm 把孤儿包挪进 node_modules/.ignored
rm -rf ~/.dsh/profiles/desktop/node_modules ~/.dsh/profiles/desktop/pnpm-lock.yaml
```

注意 pnpm 11 是**挪到 `.ignored` 而不是删除**（2.0 MB 原地不动），所以"卸载成功"之后
磁盘上仍然躺着整包——想真正回收空间必须自己删。

**修复**：`remove` 应当先跑 `pnpm remove`、成功后再 reconcile 清单；或者干脆统一成
"以清单为准"的语义（先改清单 → 跑 `pnpm install`），并在"清单已经符合预期"时把 pnpm 的
非零退出码降级为警告。无论选哪条，`.ignored` 都不该成为用户的默认收尾状态。

## 三、面板的数据面：一个还没解决的缺口

这是本次唯一"不是 bug、是缺口"的一条，单列出来，因为它决定了面板在桌面版里到底有没有用。

现场快照里写着：

```json
"remoteFace": true,
"capabilities": ["L1 · 关闭", "remote · 本地服务", "命令面 · cmdline", …]
```

`remote · 本地服务` 的意思是：host 半确实 `provide('mnemoRemote', face)` 了，但**没能挂到宿主的
remote 注册表**。而 `tools/src/bridge.ts` 的四种探测（`register` / `contribute` / `define` /
`contributions`）在 `0.2.1-rc.3` 上全部落空——因为这个版本里 **`ctx.remote` 是 client 侧服务**，
宿主侧对应的是 `@deepseek-ai/dsh-typert-registry` 的 `TypertRegistry`（`registerHost` /
`registerProvider` / `commit`），不是 `remote.register`。

而 client 侧 `ui/src/client/index.ts` 的选择顺序是：

```
ctx.get('mnemoRemote') → ctx.get('remote').mnemo → 事件源（只读） → 演示数据
```

前两条在浏览器里都拿不到宿主进程里的对象，所以面板会落到**只读事件源**：
能看，不能写（`memory_forget` / `pin` / `assert` 这些按钮走不通）。

**这不是 0.5.3 能修的**——它需要按 typert 的契约把 remote 面真正注册出去（`registerHost` +
codec + 客户端类型面），是一次 0.5.5 级别的改动。在那之前，桌面版的面板应当**明确告知
"只读"**，而不是让用户点了没反应。

> 待确认：面板在桌面窗口里的实际角标与按钮状态，本次未能截到图（无头 Edge 加载 2.1 MB
> 的组合产物时渲染进程异常退出）。建议在真实窗口里点一遍：设置 → 插件 → 记忆面板。

## 五、版本策略

`0.5.3` 十个包**已经在 npm 上**（`latest = 0.5.3`）。所以：

- D1 / D5 / D6 / D7 是**代码**，只能进 `0.5.4`；
- D2 / D3 / D4 是**文档**，可以现在就改、现在推，不必等版本号；
- **不建议 unpublish 0.5.3**：72 小时窗口内虽然可以，但会打断已经装上的用户，
  而且 D1 的症状在有人真的在空机器上装之前是不可见的——这正是它值得写进发布说明的原因。

`0.5.4` 的最小内容建议：D1 + D5 + 那条 `config-defaults` 守卫测试 + D6 的清单规则。
D7 顺手。面板数据面留给 `0.5.5`。

## 六、元问题：为什么这些缺陷都没被测出来

0.5.3 修的是"装不上"，而它自己仍然留下了"装上了但起不来"和"照文档装会装错版本"。
两者都不是逻辑错误，都是**"真实的安装器 + 全新的机器"这条路径没人走过**。

建议加一条 CI smoke（Linux + Windows 各一次，5 分钟内可跑完）：

```bash
# 1. 空 profile、空 HOME，验证 D1
export HOME=$(mktemp -d)                 # Windows: 换 USERPROFILE
dsh plugin --profile smoke add @rain13sad/dsh-mnemo-core@0.5.3 …（九包）
test ! -d "$HOME/.dsh/mnemo"             # 断言：库目录确实不存在
dsh --profile smoke --port 0 --no-open & # 启动
sleep 8
```
